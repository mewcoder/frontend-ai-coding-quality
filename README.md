# AI Coding 之前：前端工程已有的质量保障手段

本文只讨论前端工程化中的自动化质量保障手段，不包含需求评审、Code Review、手工测试和人工验收等人为介入环节。

在 AI Coding 普及之前，成熟的前端工程已经形成了一套完整的自动化质量防线：

```text
代码约束
  ↓
自动化验证
  ↓
交付保障
  ↓
线上监测
```

## 一、代码约束

代码约束的目标，是在代码运行之前，通过规则和工具减少错误产生。

典型手段包括：

- TypeScript 类型检查
- 编译检查
- ESLint、Stylelint
- 代码格式检查
- API Schema 校验
- 依赖版本锁定
- 浏览器目标和语法兼容性检查
- 静态代码安全检查

这一层主要解决：

> 代码是否符合规则，是否能够被正确编译和构建？

## 二、自动化验证

自动化验证的目标，是确认代码运行后的行为是否符合预期。

典型手段包括：

- 单元测试
- 组件测试
- 集成测试
- API 契约测试
- E2E 测试
- 快照测试和视觉回归测试
- 多浏览器自动化测试
- 自动化性能测试
- 自动化可访问性测试
- 依赖漏洞和安全扫描

这一层主要解决：

> 代码运行后，功能、兼容性、性能和安全表现是否合格？

## 三、交付保障

交付保障的目标，是阻止不合格代码进入发布流程，并控制发布过程中的未知风险。

典型手段包括：

- CI 质量门禁
- 测试覆盖率门槛
- 构建产物校验
- Bundle 体积预算
- 构建可复现性检查
- 自动化 Smoke Test
- 灰度发布
- Feature Flag
- 分批放量
- 自动停止发布
- 自动回滚

这一层主要解决：

> 不合格的代码能否被拦截？已经通过检查的代码，如何降低上线风险？

## 四、线上监测

线上监测的目标，是在真实用户环境中自动发现测试阶段未覆盖的问题。

典型手段包括：

- JavaScript 异常监测
- 白屏监测
- API 请求失败监测
- 静态资源加载失败监测
- 页面性能监测
- Core Web Vitals 监测
- 真实用户行为和环境数据采集
- 错误率和关键流程失败率监测
- 自动告警
- 异常趋势识别

这一层主要解决：

> 代码上线后，真实用户是否遇到了异常？问题是否正在扩大？

## 总结

前端工程化质量保障可以归纳为四类：

| 分类 | 核心作用 |
| --- | --- |
| 代码约束 | 减少错误产生 |
| 自动化验证 | 在发布前发现错误 |
| 交付保障 | 拦截不合格变更并控制发布风险 |
| 线上监测 | 发现真实环境中的问题 |

因此，AI Coding 之前的前端质量体系并不是依赖某一个测试工具，而是一条完整的自动化链路：

> 约束错误产生，验证代码行为，控制交付风险，监测线上结果。

## AI Coding 之后：变化与挑战

AI Coding 带来的变化，不只是代码生成方式变化，也改变了前端质量保障的重点。

### 1. 代码生成效率提升

AI 可以快速生成代码，减少重复劳动，提升功能开发和交付的速度。

### 2. 测试编写成本下降

过去前端项目中，单元测试和 E2E 测试经常因为编写、维护和补充数据的成本较高而被弱化。

AI 可以辅助生成测试、Mock 数据、测试场景、验证环境和测试脚本。因此，过去“没有时间写、成本太高”的测试，在 AI 时代变得更容易覆盖。

### 3. 代码质量风险同步增加

AI 生成的代码并不天然正确，仍然可能存在业务理解偏差、逻辑错误、隐藏回归，以及性能、安全和可维护性问题。

同时，代码生成得越快、越多，潜在问题出现和扩散的速度也可能越快。

### 4. 质量保障更加重要

AI Coding 一方面降低了测试和验证的成本，另一方面增加了需要被验证的代码数量。

因此，质量保障不再只是上线前的额外投入，而需要成为 AI Coding 流程中的基础闭环：

> AI 提高了代码生产效率，也降低了测试编写成本，但最终能否稳定交付，仍然取决于质量保障体系是否跟得上。

## AI Coding 的质量约束与开发工作流

AI Coding 需要通过一系列约束和工作流，减少生成代码的不确定性，让 AI 在明确的任务、规则和规格下完成开发。

这些机制在不同工具中的名称可能不同，但目标相同：让任务要求、项目规则和质量检查能够被 AI 持续读取和执行。

### 1. Prompt

通过 Prompt 对当前任务提出明确要求，包括任务目标、修改范围、实现方式和交付结果。

### 2. Rules / `AGENTS.md`

通过项目规则文件沉淀长期有效的开发约定，例如技术栈、目录结构、编码规范、组件使用方式和架构边界。

`AGENTS.md` 不应该变成一份巨大的项目手册，更适合作为项目地图，指向更详细的架构、测试和开发文档；目录级规则则只约束对应范围内的代码。

### 3. Skills / Commands

将常见开发任务固化成可复用的流程，让 AI 按照统一方式执行特定类型的工作。

### 4. Hooks

在 AI 执行前后自动触发与代码质量相关的检查，例如格式检查、类型检查、测试触发和结果校验。

### 5. SDD

通过规格说明、业务规则和验收标准组织开发过程，明确功能要做什么、边界是什么，以及什么结果才算完成。

这几种手段分别作用于任务指令、项目规则、开发流程、执行检查和需求规格，共同降低 AI Coding 的不确定性。

## 从项目规则到 E2E：AI Coding 质量保障实践

这一章以一次前端功能变更为例，说明 AI 如何把项目规则、代码 Review、测试生成和 E2E 验证串起来。

### 1. 项目知识与 Rules

首先让 AI 读取：

- `AGENTS.md` 和目录级 Rules
- 相关架构和业务文档
- 已有的组件、接口和测试代码
- 项目的类型检查、测试和 E2E 命令

Rules 中不仅要写代码风格，还要写清楚：哪些功能必须补测试、测试文件放在哪里、哪些状态必须覆盖，以及什么条件才算完成。

### 2. AI Code Review

代码生成后，AI 基于当前 Diff、项目 Rules 和已有测试进行 Review，重点检查：

- 业务逻辑和边界条件
- 加载、空数据和错误状态
- 组件和 API 的使用方式
- 潜在回归和不必要的修改
- 是否缺少必要的测试

Review 结果应该是可以执行的具体问题，而不是泛泛的代码总结：

```text
文件：src/pages/SearchPage.tsx
问题：接口失败时没有错误状态
风险：用户无法判断搜索是否失败
建议：增加 error 状态，并补充对应测试
```

### 3. 测试计划与测试代码生成

AI 不应直接从代码生成测试，而应先根据需求、代码变更和已有测试整理测试场景，再生成测试代码。

例如，一个搜索筛选功能至少需要覆盖：

- 正常搜索
- 筛选条件组合
- 无匹配结果
- 接口请求失败
- 加载状态
- 清空筛选条件

在此基础上，AI 可以生成：

- 单元测试
- 组件测试
- E2E 测试
- Mock 数据和测试 Fixture
- 线上问题对应的回归测试

### 4. E2E 执行、修复与回归

生成 E2E 测试后，执行项目已有的 E2E 命令，并保留失败测试的截图、Trace、控制台日志和网络信息。

失败后由 AI 分析问题属于：

- 产品代码问题
- 测试代码问题
- 测试环境问题

修复后重新执行 E2E，而不是直接修改断言或删除失败用例。确认通过后，将新发现的问题沉淀为回归测试。

最终形成：

```text
AGENTS.md / Rules
  ↓
AI Code Review
  ↓
测试计划与测试代码生成
  ↓
E2E 执行
  ↓
失败分析与修复
  ↓
回归测试沉淀
```

## 结语

AI Coding 提高了代码生产效率，也降低了测试编写成本，但并没有降低质量保障的重要性。

更可靠的方式，是让 AI 在明确的项目规则下生成代码，由 AI 参与 Review 和测试生产，再通过 E2E 等工程化手段验证真实用户流程。

> AI Coding 负责提高生产效率，工程质量体系负责验证最终结果。
